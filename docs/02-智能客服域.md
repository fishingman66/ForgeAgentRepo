# 第一部分 · 客服业务域主方案

## 一、定位与总览

客服域是独立业务模块（非平台功能挂载）：访客免登录链路、多渠道接入、七态工单与 ACD、坐席工作台、CSAT/质检/指标、FAQ 数据飞轮、合规（PII/留存/擦除），以及语音呼叫中心（AICC 对接）。

- **新增三个模块，仍单 jar 单库**：`forge-customer-service`（客服业务域）、`forge-callcenter`（语音适配层）、`forge-callcenter-common`（零业务依赖的纯契约层）。
- 依赖方向严格单向：`callcenter → customer-service → callcenter-common`；`customer-service → forge-agent（契约接口）/ forge-api / callcenter-common`，`forge-agent` **禁止**反向依赖。
- **对话执行内核零重写**：客服通过 forge-agent 暴露的 6 个契约接口（`CsChatFacade` / `CsKnowledgeGateway` / `CsRunOwnership` / `CsTraceExtender` / `CsGovernanceFacade` / `CsSessionOwnerResolver` SPI）挂载，控制台存量会话零行为变更。
- 独立开关：`agent.customer-service.enabled`（默认 true，关闭时 Bean 与端点不装配）、`agent.callcenter.enabled`（默认 false）。

```
访客接入层   网页挂件 / 独立 H5 / 公众号·企微 / OpenAPI / 电话（AICC）
     │ /chat-api/{channelCode}/**（免登录）    │ /chat-voice/{provider}/{code}（语音回调）
客服网关层   CsChannelGuard：三层限流 · HMAC 令牌 · 幂等受理 · 空间服务端解析
     │
客服业务域   forge-customer-service：访客/会话 · 工单7态 · 坐席/队列 · CSAT/质检 · FAQ · 合规
     │ 契约接口（单向）
Agent 执行域  forge-agent / rag / memory / core（编排、检索、Trace、SSE 续传、记忆）
```

## 二、关键设计决策（D1~D9 现行结论）

| # | 决策点 | 结论 | 理由 |
| --- | --- | --- | --- |
| D1 | 代码落点 | 独立模块 `forge-customer-service` | `forge-agent` 已承载十余个域；根包扫描与 `com.forgeagent.**.mapper`/`**.domain` 通配天然覆盖新模块，落地成本低于初判 |
| D2 | 访客身份与会话 | 双表映射：`agent_cs_visitor` + `agent_cs_conversation`（持 `agent_session_id`）；`agent_session` 只加 `scene/visitor_id/channel_code/cs_ticket_id` 四列，`user_id` 保持 NOT NULL 填渠道服务账号 | 改 `user_id` 可空会波及全部存量查询；业务归属、记忆作用域、统计一律以 `visitorId` 为准 |
| D3 | 记忆作用域 | 客服场景默认关闭 `agent_memory`，用 L2 会话摘要 | 访客共用服务账号记忆 = 跨访客串味，合规事故 |
| D4 | 免登录鉴权 | 渠道 `ak-` 密钥（SHA-256）+ 短期 HMAC 访客令牌；`callerWorkspaceId` 由服务端从渠道解析，**禁止前端直传 workspaceId** | 平移 `/workflow-api` 限流骨架；`ResourceAccessGuard` 纯函数旁路（Sa-Token 上下文在后台线程不可用） |
| D5 | 流式事件协议 | 既有 SSE 上追加 `cs_*` 事件 + `CsTerminalEnvelope` 终态信封，`done` 帧只加字段不改语义 | `RunEventBuffer` 续传与前端 `sse-events.ts` 纯函数分派已稳定 |
| D6 | 实时通道 | **B+C 双通道**：控制面 = `CsRealtimeTransport`(SSE) 承载文本与事件；媒体面 = 云托管 AICC 承载 SIP/RTP/ASR/TTS | WebFlux 排除（Servlet 栈不可切）；电话网进不来浏览器 WebSocket；MVC WebSocket 保持纯文本通知用途，`pushBinary` 显式抛异常 |
| D7 | 排队与分配 | 真 ACD：技能匹配 → 最小负载 → 轮询 → 超时升级 → 留言工单；条件更新抢单 | 参考项目排队是半成品（固定提示语），不能搬 |
| D8 | 知识降级 | fail-closed：零命中/低分/向量不可用 → 明确兜底话术 + 零命中沉淀 + 按策略转人工；`CsProductionReadinessValidator` 在 prod 下配置缺失拒绝启动 | 「运营以为知识库在生效」是最难查的故障（参考项目事故经验） |
| D9 | 模块形态 | `forge-callcenter` + `forge-callcenter-common`（纯契约层：事件信封、通道接口、`CsEventTypes` 21 事件常量、`CsPiiMasker`、`CsChannelSignature`） | 呼叫中心与客服共享契约但零业务依赖，换 AICC 供应商只换适配器 |

规模基线（D8）：30 坐席 / 30 路并发 / 月 40 万分钟；号码与中继留 `NumberProvider` / `TrunkProvider` 扩展接口。

## 三、实时通道（B+C 双通道）

- **控制面**（文本与事件）：`CsEventEnvelope` → `CsRealtimeTransport`（SSE 实现）→ `RunEventBuffer` 断线续传；`agent.customer-service.transport` 只有 `sse` 一个有效值；**不改**全局 `message.transport` 与 `/resource/message`（登录用户通知互不影响）。
- **媒体面**（电话音频）：PSTN → SIP 中继 → AICC 媒体网关（华为云 PoC，`CsVoiceGateway` 中立适配层）→ `/chat-voice/**` 回调（验签 + 时间窗 + nonce + callId 幂等，响应为厂商 `{message,retcode}` 格式）。
- 已作废：网页语音期设计的 `CsWebSocketHandler` / 访客握手拦截器 / `audio_chunk` / `barge_in` / `/chat-ws/**`——电话场景访客端是话机，这些组件无用武之地。
- Mock 契约（`AICC_MOCK`，仅 dev/test）：HMAC-SHA256 + 11 事件固定序列 + 固定 WAV 录音字节（`forge-callcenter/src/test/resources/mock/aicc/`），无真实 AICC 也可全链路调试。

## 四、数据模型

**新增 13 张客服表**（`agent_cs_*`，SQL：`agent_cs_c0~c4.sql`）：

| 域 | 表 |
| --- | --- |
| 渠道与身份 | `agent_cs_channel`（渠道端点：空间归属、密钥、限流、CORS、兜底话术、handoff 策略）、`agent_cs_visitor`（访客 + 同意状态 + 擦除标记）、`agent_cs_conversation`（客服会话，关联 agent_session_id） |
| 工单 | `agent_cs_ticket`（七态主表 + 首响/SLA 时间戳）、`agent_cs_ticket_event`（不可变事件轨迹，14 种事件） |
| 坐席 | `agent_cs_seat`（技能组/负载/在线/角色）、`agent_cs_queue`（排队项 + SLA deadline） |
| 消息 | `agent_cs_message_receipt`（`clientMsgId` 幂等回执，唯一键 session+client_msg_id） |
| 运营 | `agent_cs_csat`（会话级满意度）、`agent_cs_quality_rule` / `agent_cs_quality_check`（可配置质检）、`agent_cs_knowledge_answer`（FAQ 补录答案：审核 + 生效期）、`agent_cs_metric_daily`（日指标） |

**存量表幂等 ALTER**：`agent_session` +4 列（scene/visitor_id/channel_code/cs_ticket_id）、`agent_message` +3 列（client_msg_id/sender_type/ticket_id + 唯一索引）、`agent_run` +3 列（客服维度下钻）、`agent_token_usage` +1 列（渠道成本归集）、`agent_cs_channel.channel_secret`（AES-GCM 加密存取）。

DDL 细节以 `backend/sql/agent_cs_c0~c4.sql` 为准（幂等可复跑）；语音域 `agent_cc_c0/c1.sql`（`agent_cc_*` 六表 + 菜单），详见第四篇文档。

**菜单结构**（2026-11-14 整理，`backend/sql/agent_cs_menu_groups.sql`，已合入 `deploy/docker/mysql/init/02-seed.sql`）：顶级顺序固定为 **Agent平台(1) → 智能客服(2) → 其余目录从 3 起**；智能客服下由 11 个平铺页收进 3 个分组目录（与 Agent平台 的 `M` 型分组同构，`component` 为 NULL）：

| 分组 | 页面 |
| --- | --- |
| 服务运营 | 坐席工作台、运营看板、通话记录、会话满意度 |
| 智能能力 | 意图管理、知识答案、知识图谱、渠道接入 |
| 质量与合规 | 质检管理、辅助看板、合规与模板 |

脚本幂等（分组目录 `WHERE NOT EXISTS`、叶子节点按 `menu_id` 精确 UPDATE），存量库与干净库结果一致；超管自动可见全部菜单，其余角色原本未授客服菜单，无需补授权。

## 五、接口与安全

**访客端**（免登录 `/chat-api/{channelCode}/**`）：建会话（活跃复用 409）、发消息（`clientMsgId` 三态回执）、SSE 续传（`/events?after=N`）、逐字流式（`/messages/stream`）、历史游标、打断、转人工、工单用户侧流转、CSAT、消息反馈、隐私擦除。

**坐席端**（`@SaCheckLogin`，`/agent/customerservice/**`）：工单池与全流转（claim/reply/hold/resume/transfer/resolve/close/priority）、排队监控与手动派单、渠道 CRUD、坐席配置、CSAT/质检/知识答案/看板/合规审计、通话列表（`/calls`）。

**渠道回调**（`/chat-channel/**`）：公众号 XML / 企微明文模式适配，SHA1 签名 + 时间窗 + nonce + MsgId 幂等；`continuous/per_message` 会话模式。

**安全闸门**（平移自 workflow-api 并加固）：① IP 预限流 120/min（鉴权前）→ ② 密钥/令牌校验（失败单独计 10/min）→ ③ 渠道端点级限流 → ④ 256KB 请求体 → ⑤ `clientMsgId` 幂等 → ⑥ 会话锁 → ⑦ 执行；限流为 Redis 原子计数（多实例共享）、nonce 5 分钟去重、Origin 白名单强制校验；错误消息统一模糊化。

**工单七态**：`AI_SERVING → WAITING_AGENT → PROCESSING →（HOLD/RESUME）→ WAITING_CONFIRM → RESOLVED → CLOSED`，支持 cancelHandoff / reject 回流 / reopen；非法流转实体内 fast-fail 返回 409，每次流转写不可变事件轨迹。

**事件协议**（通道无关，追加不改既有语义）：`cs_accepted`、`cs_ticket_event`、`cs_queue_position`、`cs_handoff`、`cs_agent_typing`、`cs_csat_invite` + 既有 `run_id/delta/done/error`；终态 `CsTerminalEnvelope`（messageId/finishReason/usage/traceId/citations/ticketStatus/handoff/csatInvited）。

## 七、已知限制

1. 企微仅**明文模式**；加密模式（EncodingAESKey + corpId AES-CBC）未实现，上生产前补齐或继续用明文模式。
2. 存量明文 `channel_secret` 兼容可用，需一次性运维迁移才全部转密文。
3. `CsGovernanceFacadeImpl.canPublish` 为基础检查，未接入 `ReleaseGateService` 评分门禁。
4. 指标聚合为手动/接口触发（`POST /metrics/rebuild`），未接 SnailJob 定时。
5. 跨域名挂件嵌入需配置代理或启用 CORS 白名单强制校验（当前同源 `public/` 托管）。

## 八、明确不做

1. 不新增后端部署单元（单 jar 单库）；不引入 WebFlux；不自建 WebRTC/SIP 媒体网关（允许云托管媒体面接入）。
2. 不引入 Flyway / Nacos / Kafka / Neo4j / 独立向量库；Postgres/pgvector 属记忆体系范畴另行决策。
3. 不改全局 `message.transport` / `/resource/message`；不重写 `AgentChatServiceImpl` 与控制台聊天页。
4. 不复制参考项目的演示数据与 6 域 Mock 后端；订单/售后类查询走 `agent_tool` / `agent_datasource` 真实绑定。
5. 不做双状态机与兼容层；IVR 用「机器人直接应答 + 意图分流」替代按键菜单树。
6. 坐席排班、监控大屏、外呼、Prompt A/B 灰度、话术效果分桶：无真实需求不做。
7. `searchInternal` 永不暴露为 Controller 端点；`workspaceId` 永不交给前端传。

## 九、决策与取舍记录

| 决策点 | 结论 | 依据 |
| --- | --- | --- |
| 不搬实现，只借业务语义 | 移植 8 类机制：七态状态机、统一终止信封、帧协议与幂等受理、会话级锁、数据飞轮表设计、生产就绪校验（fail-fast 三道闸门）、对话阶段、迁移纪律 | 技术栈差异决定搬码不可行；参考项目事故教训「知识降级必须 fail-fast」是最有价值的移植项 |
| 不照搬的 7 类 | 演示假数据、半成品排队、硬编码质检/话术、MySQL 应用层向量、双状态机包袱、空壳死代码、默认弱凭据 | 交叉抽查源码定位；曾有一处误报（RAG 静默降级实为已修复的 fail-fast）按勘误改列为正面机制 |
| `AgentSession.user_id` 语义 | 保持 NOT NULL 作渠道服务账号占位，业务归属全走 visitorId | 改可空波及面失控 |
| 事务边界 | 跨模块不做分布式事务：先落客服域记录 → 调 `CsChatFacade` → 回写 messageId/runId；失败 `acceptance=REJECTED` + 补偿 | 与 P0 Trace「业务回滚不丢诊断」口径一致 |
| 客服分支收敛 | `AgentChatServiceImpl` 只在 `prepareRound` 开归属解析 SPI，执行链零改动 | 避免超大编排类继续膨胀 |
| WebFlux 排除 | Servlet 栈同时引入 webflux starter 仍以 MVC 为准；真切 reactive 等于全栈重写 | 运行时（Reactor）与传输协议（SSE/WS）是两个维度，不可混谈 |
| Lombok 构造陷阱 | `@RequiredArgsConstructor` 类不要手写额外构造器（Spring 报 No default constructor found） | C4 首启失败的实际原因 |
| 历史假绿 | 单测「EXIT=0」不等于跑过，验证必须读 surefire 报告 | V0.5 修正过一处历史假绿口径 |

# 第二部分 · 对标增强交付（P0~P3）

对标典型客服智能体：只看现有功能差异与测试支撑的能力。对标结论——客服骨架完整可用，差距不在「能不能接待客户」，而在三个更深的位置：对话智能密度、运营改进闭环、企业级约束；

## P1 · 运营改进闭环（`p1_verify.py` 44/44）

| 决策点 | 结论 | 依据 |

# 第三部分 · 坐席辅助（Agent Assist，A1~A5）

坐席辅助是一条**异步旁路**：访客消息落库（文本）或转写分片定稿（语音）后由事件钩子触发推荐服务，检索结果经控制面通道推给坐席界面；`send` 同步链路零改动，访客应答时延不受影响。

```
访客消息落库(文本) ─┐
                    ├─► SeatAssistService（异步旁路）
转写定稿(语音) ─────┘        │ 检索内核：RAG 混合检索 + FAQ 直取
                             ▼
              候选话术(top3) + 意图标签 + 建议操作
                             │ SEAT_SUGGEST 信封（payload 只增不改）
                             ▼
        CsRealtimeTransport → 坐席工作台推荐面板（采纳=填入输入框）
                             │ 采纳 / 忽略埋点 → 效果指标 → FAQ 飞轮回流
```

- 采纳交互：**采纳 = 自动填入坐席输入框**（保留修改权，系统不代发）；忽略 = 本会话静默同类推荐。
- 独立参数在 `agent.customer-service.assist.*`（节流秒数、ASR 最低置信度、回流开关/窗口/上限）。

## 能力现状（A1~A5）

| 期 | 能力 | 现状 |
| --- | --- | --- |
| A1 | 文本话术推荐 MVP | `CsVisitorMessageSavedEvent`（落库后发布，幂等重放不发）→ `SeatAssistService`（@Async 旁路，FAQ 直取 + RAG 混合检索，top3 硬上限，空候选不推卡片）→ 落库 `agent_cs_seat_suggestion` → 坐席面板轮询拉取（5s）；反馈端点 `POST /agent/customerservice/suggestions/{id}/feedback` |
| A2 | 语音转写触发 | 定稿分片（`is_final='1'`）经 说话人黑名单 → 置信度阈值（默认 0.6）→ 会话已绑定 → 节流（默认 10s，Redis `trySet` 按**通话**维度）五道判定进入同一推荐服务；推荐带 `source=voice` + `call_id` 溯源；转写上屏 payload 只带脱敏后文本 |
| A3 | 意图体系 | `agent_cs_intent`（平台级 + 空间级，5 条平台种子）+ 管理页（平台级只读）；规则打标（priority 升序首个命中），未命中用最近 3 轮访客原话兜底；意图 `kb_ids` 并入检索范围 + 命中分片加权重排；**LLM 分类未做**（接入点 `CsIntentService.classify` 已预留） |

## 关键口径

1. **协议演进**：`SEAT_SUGGEST` payload 只增不改（intent / intentName / actions 为后续追加）；top3 为协议常量，调整需同步前后端。
2. **呈现方式**：坐席面板为轻轮询（5s）拉取——当时坐席端无 SSE 订阅基建；P3-2 坐席 SSE 通道交付后可实时化。
3. **意图呈现**：推荐记录存意图**编码**（稳定聚合键），卡片按名称展示、历史数据回退编码。
4. **回流规则**：连续 3 条全部未采纳才回流——单条未采纳常是时机不对，连续 3 条才是「这类问题答不好」的信号。
5. **运营入口**：意图管理（菜单 40010）、辅助看板（菜单 40011）。

## 明确不做（第三部分）

1. 不全自动代答（只建议不代发）；不开放「触发工作流」动作。
2. A3 不做 LLM 意图分类；不做独立坐席话术表（候选话术由 FAQ 候选承担）。
3. 不新建坐席端实时订阅链路（P3-2 的 SSE 通道已可承载）。
4. 语音留言消息（会话内语音文件）不在范围；访客侧行为零变更。

## 决策与取舍记录（第三部分）

| 决策点 | 结论 | 依据 |
| --- | --- | --- |
| 推荐异步化 | 挂事件监听，不进 `send` 同步链路 | 推荐慢或失败只影响坐席体验，访客零感知 |
| 意图先规则后模型 | A1 用 FAQ 命中即意图、A3 规则打标先行 | 零成本零延迟先让数据跑起来 |
| 节流按通话维度 | Redis `trySet` 键 `cs:assist:voice:{callId}` | 一通电话内 ASR 定稿分片密集；Redis 不可用降级放行 |
| 事件信封结构 | 端点 `data` 是完整信封 JSON，业务字段在 `payload` 里 | A2 修掉 A1 遗留缺陷：直接按 `data.suggestionId` 取值恒 undefined，`payloadOf` 统一解包后实时卡片才生效 |
| 回归范围裁剪 | 回归 = 被改动触达的链路 + 编译冒烟，四条全量回归链不仪式性重跑 | A2 改动面为新增触发点与只增字段 |
| 登录加密 | e2e 登录走 `@ApiEncrypt`：AES key 为 32 位 hex 字符串的 ASCII 字节，RSA 加密其 base64 作 `encrypt-key` 头（工具 `temp/A1Login.java`） | A1 调试坑；`admin` user_id 是雪花 ID，坐席行按实际 user_id 种 |
