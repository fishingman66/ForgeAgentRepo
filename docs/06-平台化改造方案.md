# 一、Agent 平台 SQL 的 PostgreSQL 方言

## 1.1 现状盘点（实测）

**脚本侧**

| 事实 | 数据 |
| --- | --- |
| 脚本总数 | `backend/sql/*.sql` 共 **78** 个（另 `forge_kg_core.sql` 在内） |
| 幂等壳 | 16 个文件用 `CREATE PROCEDURE` + `information_schema` + `PREPARE/EXECUTE` 做「加列/加索引前判断」 |
| 非幂等源 | 52 个文件含 `ALTER TABLE`（靠上面的壳保护），37 个含 `AUTO_INCREMENT` |
| 类型 | `DATETIME` 43、`utf8mb4` 48、`ENGINE=InnoDB` 40、`LONGTEXT/MEDIUMTEXT` 12、`TINYINT` 9、`JSON` 1（`agent_kb_r5_scale.sql`） |
| 索引 | `FULLTEXT ... WITH PARSER ngram` 1 处（`agent_hybrid_search.sql`；已折进 `deploy/docker/mysql/init/01-schema.sql:233`） |
| 部署真源 | Docker 只服务 MySQL：`deploy/docker/mysql/init/01-schema.sql`（**128 表**，与开发库零差异）+ `02-seed` + `03-demo` |

**基座侧**

- `backend/script/sql/postgres/` 已有 `forge_vue.sql` / `forge_workflow.sql` / `forge_job.sql` 三份，**不含任何 `agent_*` 业务表**。
- `application-dev.yml` 硬编码 `com.mysql.cj.jdbc.Driver`，`dynamic` 数据源里的 `postgres` 段整段被注释（ruoyi 遗留）。
- 分页插件 `new PaginationInnerInterceptor()` **未指定 `DbType`** → MyBatis-Plus 按 JDBC URL 自动识别方言，**这一层不用改**。
- 项目**没有** `DatabaseIdProvider`，MyBatis 的 `databaseId` 机制未启用。

## 1.2 Java 侧 MySQL 专有 SQL 全清单（8 处，已逐条核实）

| # | 位置 | MySQL 写法 | PG 等价 |
| --- | --- | --- | --- |
| 1 | `AgentKbChunkMapper#searchByKeyword`（2 处：`SELECT` 投影 + `WHERE`） | `MATCH(c.content) AGAINST(#{q} IN NATURAL LANGUAGE MODE)` | `to_tsvector('simple', c.content) @@ plainto_tsquery('simple', #{q})`，排序 `ts_rank_cd`；中文需 zhparser，无则降级 `pg_trgm` |
| 2 | `KgNodeMapper`（`@Insert`） | `ON DUPLICATE KEY UPDATE salience = salience + 1, ...` | `ON CONFLICT (scope_type, scope_id, user_id, name_key) DO UPDATE SET ...` |
| 3 | `AgentTokenUsageDailyMapper`（`@Insert`） | `ON DUPLICATE KEY UPDATE ...`（依赖 `uk_dim`） | 同上，冲突键用 `uk_dim` 对应列 |
| 4 | `CsKgExpandMetricMapper#bump` | `ON DUPLICATE KEY UPDATE total_searches = total_searches + 1, ...` | 同上 |
| 5 | `CsKgExpandMetricMapper#selectRecent` | `DATE_SUB(CURDATE(), INTERVAL #{days} DAY)` | `CURRENT_DATE - make_interval(days => #{days})` |
| 6 | `WorkflowSchemaGuard`（2 处） | `information_schema.tables/columns` + `DATABASE()` | `current_schema()`；`is_nullable='NO'` 通用，只需换 schema 函数 |
| 7 | `SqlQueryService`（表结构快照，2 处） | `information_schema.*.table_comment` / `column_comment` | PG 无 comment 列 → `obj_description(c.oid)` / `col_description(c.oid, a.attnum)` |
| 8 | `AgentKbChunk.embedding` 列 | `BLOB`（float32 小端） | `bytea`；**应用层编解码零改** |

> 补充：`SqlQueryService` 是给「平台用户自己的数据源」执行问数 SQL 的，那条链路的方言由 `agent_datasource.db_type` 决定，**不属于本次范围**；只需修它的**表结构内省**（#7）在 PG 主库上跑得通。

## 1.3 方案选择

| 路线 | 做法 | 判断 |
| --- | --- | --- |
| A. 逐脚本翻译 | 把 78 个增量脚本翻成 PG（存储过程壳换 PL/pgSQL） | **否**。工作量大，且以后每次迭代都要双写同步，必然漂移 |
| B. 单一基线 + 双目标生成 | 以已对齐开发库的 `01-schema.sql`（128 表）为唯一真源，生成 PG DDL；78 个增量脚本**不翻译**，只服务 MySQL 存量升级线 | **推荐** |
| C. 引入 Flyway/Liquibase | 全部脚本改 versioned migration，双库各一套 changelog | 更彻底但侵入大；建议作为「确定长期双库维护」时的升级路径 |

**推荐 B 的理由**：`01-schema.sql` 刚刚完成与开发库的零差异对齐（128 表 + 48 个增量列已折进建表定义、0 条 `ALTER TABLE`、可重复执行），它**本身就是一份干净的全量基线**——这是做跨方言生成的最佳时机，越往后拖成本越高。

**关键取舍**：`backend/sql/` 78 个脚本的定位降级为「MySQL 存量库升级历史」，新库（无论 MySQL 还是 PG）一律从基线建起。这与当前 Docker 的做法一致。

## 1.4 实施步骤

### P0 方言识别与开关

- 新增 `forge.db.dialect`（取值 `mysql` / `postgres`），默认**从 `spring.datasource.dynamic.datasource.master.url` 前缀推断**，避免手配与实际连接不一致。
- 注册 MyBatis `VendorDatabaseIdProvider`（`MySQL` → `mysql`，`PostgreSQL` → `postgresql`），使 XML mapper 可用 `databaseId` 双版本。
- 注意：MyBatis **注解 `@Select` 不支持 databaseId**，所以 #1~#7 里凡是注解形式的 SQL，要么迁到 XML，要么走 SPI（见下）。

### P1 三类专有 SQL 的落法

| 类别 | 清单 | 落法 |
| --- | --- | --- |
| **Upsert（3 处）** | #2 #3 #4 | 迁到 `resources/mapper/**/*.xml`，同 `id` 两个 `<insert databaseId="mysql">` / `<insert databaseId="postgresql">`。SQL 原样保留，改动最小、可读性最好 |
| **内省（3 处）** | #6 #7 | 抽 `DbSchemaIntrospector` SPI（`mysqlSchemaIntrospector` / `postgresSchemaIntrospector`），按 `forge.db.dialect` 选 Bean。这类 SQL 长且各库差异大，塞进 XML 反而更乱 |
| **全文检索（1 处）** | #1 | 抽 `KbKeywordSearch` SPI（见 P3）。**不能**只换 SQL——PG 无 zhparser 时需要额外降级逻辑 |

选用 SPI 而非 XML 的第二类/第三类，与项目既有惯例一致（`KgStore` 按 `kg.backend` 选、`EmbeddingFactory`、`ScoreThresholdPolicy` 都是这个模式），二次开发者一眼能懂。

### P2 DDL 生成器

一次性脚本 `temp/gen_pg_ddl.py`，输入 `deploy/docker/mysql/init/01-schema.sql`，输出：

- `backend/script/sql/postgres/agent_platform.sql`（随基座三份一起交付）
- `deploy/docker/postgres/init/01-schema.sql`（Docker PG 新库真源）

映射表（**必须写成表驱动，不要逐条手改**）：

| MySQL | PG |
| --- | --- |
| `bigint ... auto_increment` + `primary key` | `bigserial primary key`（或 `bigint generated by default as identity`） |
| `datetime` | `timestamp` |
| `tinyint` | `smallint` |
| `longtext` / `mediumtext` / `text` | `text` |
| `blob` / `longblob` | `bytea` |
| `json` | `jsonb` |
| `varchar(n)` / `char(n)` / `int` / `smallint` / `decimal` | 原样 |
| `ENGINE=... COLLATE=... CHARSET=...` | 丢弃 |
| 列/表 `COMMENT '...'` | `comment on column/table` |
| 行内 `KEY idx(a,b)` | `create index idx on t(a,b)`（挪到建表后） |
| 行内 `UNIQUE KEY uk(a)` | `constraint uk unique (a)` 留在表内 |
| 反引号 | 去掉（标识符全小写） |
| `CREATE TABLE IF NOT EXISTS` | 保留（PG 支持） |
| `FULLTEXT KEY ... WITH PARSER ngram` | 丢弃，改为 P4 的 GIN 索引 |

解析器复用上一轮做 schema 补全时的 SQL 感知扫描（跳过引号 / 行注释 / 块注释后再数括号），**不要用正则数括号**——`flow_node.permission_flag` 的 `COMMENT '...用@@隔开)'` 里含 ASCII 右括号，曾把建表体截断。

### P3 全文检索可用性探测

- 启动时探测：`SELECT 1 FROM pg_extension WHERE extname = 'zhparser'`，以及 `pg_trgm`、`pg_bigm` 是否存在。
- `KbKeywordSearch` 三级实现：`pgZhparser`（中文分词）→ `pgTrgm`（`%`/`similarity`，无词概念，只能做模糊召回）→ `none`（关键词路直接跳过，**记 `degraded=true` 并写 `keyword=none` 到 `SearchOutcome`**）。
- 探测结果日志**只告警一次**（`AtomicReference` 按值去重，项目既有惯例）。
- 索引：`create index ft_chunk_content on agent_kb_chunk using gin (to_tsvector('simple', content))`。

### P4 向量列

- `agent_kb_chunk.embedding` → `bytea`，`embedding_dim` → `smallint`。`memory.vector` 那条链路（`agent_memory` 向量列）同理，一并覆盖。
- 应用层「float32 小端 + 余弦」编码**一行都不用改**。
- 若日后要上 pgvector：`vector(384)` + `<=>` 算子属**独立一期**，不在本方案内（与 `docs/03` 里「pgvector 全局后置」的口径一致）。

### P5 seed / demo 移植

| 文件 | 移植点 |
| --- | --- |
| `02-seed.sql`（261 菜单） | `INSERT ... SELECT ... FROM DUAL WHERE NOT EXISTS` → PG 去掉 `FROM DUAL`；更简洁的写法是 `ON CONFLICT (menu_id) DO NOTHING`（PG 原生支持，比 MySQL 的 DUAL 技巧干净） |
| `03-demo.sql` | `SET @d = DATABASE()` + `PREPARE` 动态 GRANT → PG 直接 `GRANT SELECT ON ALL TABLES IN SCHEMA public TO forge_demo;` + `ALTER DEFAULT PRIVILEGES` |
| `demo/reset.sql` | `SET @demo_user := ...` 全局变量 → PG 用 `\set` 或 CTE；`DELETE` 顺序不变（先子表后主表） |

### P6 部署与验证

- 新增 `deploy/docker/postgres/`（`init/01~03`）+ compose 加 `postgres` 服务、用 `--profile postgres` 与 MySQL 互斥。
- **本机 Docker 不可用**，验证路径：
  1. 本机起 PG 实例，全量执行 `01-schema.sql` → **再执行一遍**验幂等（`CREATE TABLE IF NOT EXISTS` + `create index if not exists` 必须都带 `if not exists`）。
  2. 分组跑与 SQL 强相关的用例：`forge-rag`（181）、`forge-agent`（73）、`forge-kg`（20）。这三组覆盖了 #1~#7 全清单。
  3. **基线评测必须重定版本号**：PG 的关键词路实现与 MySQL ngram 不同，`HitRate@5 93.33% / MRR 0.8667 / NDCG@5 0.8841` 是 MySQL 基线，不能拿来对比。按 `docs/baseline/` 的约定存为新的 `r1-pg`。
  4. PG 版评测**不需要** `OPTIMIZE TABLE`（GIN 索引不会因删除行异步改 IDF），可复现前提从三条减为两条——反而更稳。

## 1.5 不做 / 明确不承诺

- **不做**：78 个增量脚本的 PG 翻译（含 16 个存储过程壳）。
- **不承诺**：中文全文检索与 MySQL ngram 等价。zhparser 是词粒度分词，ngram 是 2-gram 滑窗，召回集合与排序都会变；能做的是「降级要可见」，不是「结果一致」。
- **不承诺**：`agent_text2sql` 在 PG 数据源上的执行（那是 `db_type` 驱动的另一条链路，已支持）。
- 不引入 Flyway（保留为后续选项）。

# 二、MCP 服务器的空间归属

## 2.1 现状盘点（四个缺口，不止「表少一列」）

资源域双模式已经在 `agent_tool` / `agent_datasource` / `agent_model` 三张表上落地（`backend/sql/agent_resource_scope.sql`：`workspace_id IS NULL` = 平台共享，非空 = 空间私有），并由 `forge-agent-core` 的 `ResourceAccessGuard` 统一收口。**MCP 是三类资源里唯一漏掉的**，而且缺口是四处：

| # | 缺口 | 证据 | 对照组（工具） |
| --- | --- | --- | --- |
| 1 | **表无归属列** | `agent_mcp.sql` 建表 / `deploy/docker/mysql/init/01-schema.sql:415` 均无 `workspace_id` | `agent_tool.workspace_id` + `idx_tool_ws` |
| 2 | **列表无可见性下推** | `AgentMcpServerServiceImpl#queryPageList` 只按 keyword/status 过滤 | `AgentToolServiceImpl:46` 有 `resourceGuard.applyVisible(wrapper, AgentTool::getWorkspaceId)` |
| 3 | **详情/改/删/停用/测连无校验** | `queryById` / `updateByBo` / `changeStatus` / `deleteByIds` / `testConnection` 全无 `assertReadable` / `assertWritable` → **任何登录用户可读改删任意 MCP，可对任意 URL 发起连接探测** | `AgentToolServiceImpl:55,82,99,112` 均有 |
| 4 | **绑定与执行链路无归属校验** | `AgentInfoServiceImpl#validateBindings` 的 MCP 分支只查「存在」；`ChatContextAssembler#loadMcpDefs(List<Long>)` 连 workspace 参数都没有 | 工具/模型分支都走 `resourceGuard.assertReadableBy(...)`；`loadToolDefs(toolIds, callerWorkspaceId)` 有参数 |

另外：`checkNameUnique` 是**全局唯一**（无 workspace 条件），私有资源会被别的空间的同名共享资源挡住。

> 风险等级：缺口 3 里的 `testConnection` 最重——它会让服端去连任意注册的 URL。加 `assertReadable` 只是止血；SSRF 级防护（禁内网、禁重定向）目前只在 `http` 节点（`guardHttpUrl`）和知识库外部源（`SsrfGuard`）做了，MCP 的 `url` 字段**没有**。建议同批补一条内网地址校验（见 §2.4）。

## 2.2 实施步骤

### S1 数据模型

新增幂等脚本 `backend/sql/agent_mcp_scope.sql`，**照抄 `agent_resource_scope.sql` 的存储过程壳**（`forge_scope_add_column` / `forge_scope_add_index` 用 `information_schema` + `PREPARE` 做判断）→ 可重复执行：

```sql

    '`workspace_id` BIGINT NULL COMMENT ''归属工作空间(NULL=平台共享,非空=空间私有)'' AFTER `id`');
CALL forge_scope_add_index('agent_mcp_server', 'idx_mcp_ws',
    '`idx_mcp_ws` (`workspace_id`, `del_flag`)');
```

同时**必须同改** `deploy/docker/mysql/init/01-schema.sql` 的 `agent_mcp_server` 建表定义（该文件是 Docker 新库的唯一真源，上一轮刚做完 128 表零差异，别再让它漂）。

存量数据全部为 `NULL` → 全部按「平台共享」解释 → **上线零行为变更**。

### S2 服务层（照 `AgentToolServiceImpl` 逐行对齐）

- 菜单与权限**不动**（沿用 `agent:mcp:*`）。

### S5 测试（`@Tag("dev")`，新增 1 个类）

`AgentMcpServerServiceImplTest`：

1. 普通用户建共享 MCP → 拒绝；

## 2.3 兼容与回滚

- 上线后存量全为「共享」→ 行为与今天一致；普通用户仍可见全部存量 MCP。
- 若某空间要建私有 MCP：新建时选「空间私有」；**存量 MCP 不能改归属**（`update.setWorkspaceId(null)`），要迁移只能新建 + 重绑 Agent，与 tool/model 现有口径一致。
- 回滚：`agent.resource-sharing.enabled=false` 一键把全部资源按私有解释（仅运维收紧用），或直接回滚代码（多出的列留空无害）。

## 2.4 建议同批补的一条（超出原需求）

MCP `url` 是服务端主动连接的地址，当前**无任何 SSRF 防护**。建议在 `AgentMcpServerServiceImpl#validateConfig` 里加与 `WorkflowSchemaGuard` / `SsrfGuard` 同口径的校验：仅 `http`/`https`、拒内网/回环/链路本地地址、禁重定向跟随。这是 4 行左右的工具方法复用，不必单开一期。

# 三、`AgentWorkflowServiceImpl` 拆分

## 3.1 现状盘点（实测）

- **2054 行 + 62 个方法**，单类承担 5 类职责。
- **零单测**：`forge-agent` 里与工作流相关的测试只有 `WorkflowExpressionEngineTest` 和 `WorkflowGraphValidatorTest`——都是**已经抽出去的纯逻辑类**。主执行体本身一条测试都没有。

## 3.3 执行顺序（**不能先动刀**）

| 步 | 内容 | 为什么在这一步 |
| --- | --- | --- |
| **S0** | **补表征测试**（前置必做） | 现在零测试，拆完无从判断行为是否等价。这一步不做，后面五步全是赌博 |
| S1 | 抽 `WorkflowTraceCodec` | 无外部依赖，最安全，先吃掉 ~80 行建立信心 |
| S2 | 抽 6 个节点执行器 + Dispatcher | `executeNode` 的 92 行 `switch` 变成查表；每类节点独立可测 |
| S3 | 抽 `WorkflowGraphEngine` + `WorkflowNodeRunner` | 行数最大的一块；同时处理 §3.4 的登录态缺陷 |
| S4 | 抽 `WorkflowRunLauncher` | 只搬不改造；`@Transactional` 边界保持原样 |
| S5 | 核实定时清扫的调度状态 | 实施中查明二者已有 `@Scheduled`，保持现状不搬 |

### S0 表征测试的最小集合（8~10 条）

顺序图；条件分支（按 `branchName` 关联 + 无名出边的旧下标兼容）；`parallel` → `join` 归并（含 vars `putIfAbsent` 语义与 `joinName.output` 汇总 JSON）；`loop`；`goto` 失败跳转；节点重试；节点级超时；审批暂停 → `resumeRun` 续跑（`completed`/`skipped` 非空时出边视为已触发的恢复语义）；`dryRun` 桩输出。

断言口径：`WorkflowTrialRunVo`（`status` + `nodeTrace` 序列 + `vars`），**外部依赖全用 Mockito 桩**（不连库、不连 LLM、不起 sandbox），这样能在 1 秒内跑完并进 dev profile。

### S5 定时清扫状态（**方案原判有误，实施时更正**）

方案初稿把 `sweepStaleRuns` / `sweepExpiredApprovals` 判为「不在接口、零调用、无 `@Scheduled` 的死代码」。
**实施时逐行复核发现是错的**：两者都带
`@org.springframework.scheduling.annotation.Scheduled(fixedDelay = 300_000L, ...)`，
只是写成了**全限定名**，初稿用 `grep '@Scheduled'` 检索时漏检。它们一直由 Spring 定时调度，
分别负责 30 分钟僵尸 `running` 实例兜底、过期 `pending` 审批单与关联运行实例收口，
进程重启后的悬挂状态已有兜底，**不需要再接 handler**。

因此本轮 S5 改为「保持现状」：两个方法继续留在 `AgentWorkflowServiceImpl` 门面，
不搬进 `WorkflowRunLauncher`（避免两个 Bean 各注册一份 `@Scheduled` 造成双跑）。
这是本方案唯一一处事实更正，其余结论不受影响。

## 3.4 已定位的两个既有缺陷（实施状态见各节末）

> 两项均属**拆分前就存在**的行为，不是本次改造引入的。缺陷一需跨模块改造，本轮按
> 「先交付可验证的拆分」原则单独留到下一期；缺陷二随之一起保留。详见文末「实施结果」。

### 缺陷一：并行分支丢登录态（已核实，属静默降级）

`executeParallelNode` 用 `CompletableFuture.supplyAsync(..., WORKFLOW_EXECUTOR)` 提交分支任务，**没有传递 Sa-Token 上下文**。而 `LoginHelper.getUserId()` 的实现是：

```java
private static Object getExtra(String key) {
    try { return StpUtil.getExtra(key); } catch (Exception e) { return null; }   // 吞异常，返回 null
}
```

即**不抛异常、静默返回 `null`**。后果链：

1. 分支里的 `knowledge` 节点 → `DocVisibilityResolver:154` 拿到 `userId = null`；
2. ACL 角色集为空 → `RESTRICTED` 文档全部判不可见；
3. 表现为**召回变少但不报错**，`SearchOutcome` 也不会标 `degraded`；
4. `LoginHelper.isSuperAdmin()` 同样失真，超管在分支内掉权限。

修法：提交前快照 `LoginUser`，子线程内恢复上下文（`SaHolder` / `ThreadLocal`），`finally` 清理。**S3 抽 engine 时一起做**——那是全类唯一集中提交并行任务的地方，改一次就够。

### 缺陷二：节点级超时路径同病

`EXTERNAL_NODE_TYPES` 的注释写着「节点级超时不覆盖 knowledge，避免脱离登录态线程」——说明作者已知这个问题，但 `NODE_TIMEOUT_EXECUTOR`（`newVirtualThreadPerTaskExecutor`）同样是新线程，**同一缺陷在超时路径也存在**。上下文透传修完后，可以把 `knowledge` 纳入节点级超时，`EXTERNAL_NODE_TYPES` 的特例注释即可删除。

## 3.5 不做

- 不用 `@Transactional` 包裹整个执行（长时间外部调用不能持事务）。现状只有 `saveWorkflow` 和 `rollbackVersion` 带事务，`doExecuteRun` **没有**——保持现状，拆分时别顺手加。
- 不动 `WorkflowTrialRunVo` / `NodeTrace` 的数据结构（前端契约不变）。
- 不为 workflow 单开 Maven 模块（同模块内分包足够，依赖方向不变）。
