# 11 · 智能客服架构对标与增强方案

> 状态：方案（2026-11-18）· **批次 A/B/C 全部交付（2026-11-18）**：A1B/A3/A2/A1 终态 + B1/B2/B3 + C1/C2/C3/C5 工具护栏（agent 155 / cs 109 / 全仓 750 用例 0 失败；C4 异步 HITL 为明确残留，见批次 C 小节）。实施中发现并修复一个既有缺陷——CS 链路检索走登录态成员校验，访客无 Sa-Token 时被逐库吞成静默零命中（详见 A2 小节）· 对标物：《智能客服 Agent 架构文档》（四层主链路 + 人工旁路 + 横切治理，含 3 处架构取舍）
> 方法：以对标文档的 L1~L4 / 旁路 / 横切为基准框架，逐层核对 ForgeAgent 现网代码（forge-customer-service / forge-agent / forge-callcenter），只列有代码证据的差异，再按收益 / 风险 / 改动面排出增强批次。
> 结论先行：**客服骨架与横切基础强于对标文档**（渠道安全、工单状态机、坐席辅助、追踪续传均超出）；真正的差距集中在四处结构性断点——**①工具层被知识命中短路、②护栏层缺业务对象校验、③编排层缺每轮意图情绪收口、④发布链路无灰度**。全文围绕这四点展开。

## 二、四个结构性断点（附代码证据）

### 2.1 知识命中被当成唯一闸门，工具层整体被短路（最严重）

`CsVisitorService.send()`（forge-customer-service/service/CsVisitorService.java）主链路：

```java
List<KnowledgeSearchHitVo> hits = knowledgeGateway.search(workspaceId, knowledgeIds, expansion.query());
if (hits.isEmpty()) {
    // 直接兜底 + 建单转人工，不进 chatFacade
    reply = localePolicy.resolveFallback(channel, content);
} else {
    ChatSendVo vo = chatFacade.send(...);   // 此时 agent 链内部还会再检索一遍
}
```

后果：

1. 「查订单」「查物流」这类**纯查询意图**，只要知识库没有对应 FAQ，模型连 SQL/HTTP 工具都调不到，直接吃兜底话术。对标文档 L3 三类工具里两类（查询、操作）在客服访客链路上名存实亡。
2. **检索跑两遍**：CS 层 `knowledgeGateway.search` 预检一次，`chatFacade.send` → `AgentChatServiceImpl.retrieveKnowledge` 又检索一次，时延和 token 成本双倍。
3. `ChatSendVo` 只有 sessionId + 两条消息，**没有 fallback / citations / 零命中信号**，CS 层被迫自己做预检来判定兜底——这正是当初加预检的原因，属于契约能力不足导致的绕行。

### 2.2 护栏层只有「平台级」，没有「业务级」

- 归属校验：访客是免登录 HMAC 令牌（`X-Visitor-Token`），**没有登录态与业务主体绑定**，「这个订单是不是这个访客的」在当前架构上无从校验。这是对标文档 L4 第一道闸门，也是操作类工具的前提。
- 额度频次：`CsQuotaService` 是空间当日 token 口径，防的是成本失控，不是业务风险（对标口径是「金额阈值 + 单日操作次数」）。
- 幂等：`agent_cs_message_receipt` 只管消息，退款类写操作重试会真的重放。
- 审计：工具调用在 agent_run / trace 有技术留痕，但 `agent_cs_audit_log` 没有业务维度记录，不满足「操作类全量留痕」。

### 2.3 编排层缺每轮信号收口

对标文档要求「意图 + 情绪每轮必执行，结果输入对话 Agent」。现状是信号计算散落且不进主链路：

- 意图：5 个旁路点各自 `classify`，互不共享结果；
- 情绪：文本侧完全没有（语音侧 insight 包有现成 SPI）；
- 转人工：`send()` 里 5 处散落 if（敏感词 / 关键词 / 配额 / 槽位 / 零命中），没有 `HandoffDecision` 抽象，加一条规则要改主链路代码——与「规则优先于模型」的取舍①精神不符（规则应该可配置，而不是硬编码）。

### 2.4 发布链路无灰度，门禁半接线

- 全仓无 canary / 流量比例概念；`agent_info` 有 `published_version` 与 `agent_version.snapshot_json`（不可变配置快照），但对话链路只按 `agent_info` 实时装配，快照只服务于回滚记录。
- `CsGovernanceFacadeImpl.canPublish` 是手写 SQL 基础检查；`ReleaseGateService`（评测分门禁 min_eval_score）已存在却没接——这是 docs/02 已知限制 3，改动量极小但一直没做。

## 三、增强方案（四个批次）

排序原则：先修「断点」（影响正确性与能力覆盖），再补「深度」（智能密度），最后补「治理」（发布与指标）。每批独立可验证、可回退，不互相阻塞。

### 批次 A：主链路修正（正确性，最优先）

**A1 拆除知识命中闸门**

- 方案 A（终态）：`CsChatRequest` 契约不动，`ChatSendVo` 增加 `fallback` / `zeroHit` / `citationCount` 字段（只增不改），CS 层删除 `knowledgeGateway.search` 预检，兜底判定改看 facade 返回信号。
  - 得到：检索只跑一遍，意图判定交给 IntentRouter（已存在），工具路径畅通。
  - 放弃：CS 层失去「零命中先兜底」的快速短路，纯知识缺口问题的响应多一次模型调用（可用意图白名单弥补，见 A3）。
- 方案 B（过渡）：预检保留，但闸门条件从「零命中」改为「零命中 **且** 该会话 Agent 无已装配工具」（`agent_info` tool_ids 为空时才短路）。
  - 得到：改动一处条件，立即放开工具路径；存量无工具 Agent 行为不变。
  - 放弃：检索仍是两遍；「有工具但本轮不该用」的场景多花一次模型调用。
- **建议：B 立即做，A 列为契约演进的下一批**（A 需要 ChatSendVo 加字段 + 全链路回归，单独成批）。

**A1 终态信号贯通（已交付 2026-11-18，终态形态修订）**

原设想的「删除 CS 预检、改看 facade 返回信号」在 A2 之后不再是正确终态：预检已经升级为链路同构检索并被复用（删除它反而破坏流式路径的生成前闸门）。最终形态：

1. `ChatSendVo` 增加 `zeroHit`（绑定 KB 且 KB 命中为 0，附件不计入；口径 helper `zeroHitOf` 有独立单测）与 `citationCount`（R4-2 校验通过的引用条数），由 `finishRound` 从 buildMetrics / Round 回填；预算兜底分支不填。
2. CS send() 的运营信号（缺口归并 + badcase）统一改由链路权威信号驱动：`vo.getZeroHit()` 为真才记。比 A1B 的无条件记录多覆盖一类场景——**闸门有命中但链路检索零命中**（渠道 KB 与 Agent KB 不一致、预取被弃用），这类此前会被漏记；工具放行分支行为不变（该分支 zeroHit 恒真）。
3. 流式路径不加信号：其闸门必须生成前判定（chunk 已推流无法撤回），预取复用已保证闸门与应答同源，无需事后信号。

**A2 检索结果复用（已交付 2026-11-18，实现比原设想更进一步）**

实施中发现一个**既有缺陷**：链路检索 `searchOutcome` 走 `checkWsReadable` 登录态校验（`LoginHelper.getUserId` 无登录态返 null → `checkWsMember` 抛「不是空间成员」→ 被逐库 try/catch 吞掉），即 CS 访客的二次检索对非全局知识库**一直是静默零命中**，RAG 资料块长期为「暂无相关资料」。因此 A2 的落地形态是「复用 + 修复」：

1. rag 层新增 `searchInternalOutcome`（与 `searchInternal` 同一套 callerWorkspaceId 归属校验，但返回完整 SearchOutcome）；`ChatRetrievalSupport.retrieveKnowledge` 增加免登录 caller 重载（callerWorkspaceId 非空走内部口径，为空行为不变）。
2. `CsKnowledgeGateway` 新增 `retrieve`：走 ChatRetrievalSupport **完整管线**（阈值/跨库 RRF/邻块扩展/父块注入/token 预算），产出链路同构结果；CS 闸门与模型应答首次同源（旧闸门用裸 searchInternal hits，与链路口径存在裂缝）。
3. `CsChatRequest.PrefetchedRetrieval`（query + knowledgeIds + hits + contextByChunk）随请求透传；`AgentChatServiceImpl` 按既有瞬态字段先例（callerWorkspaceId 同款）经 `AgentSession` 穿透进 buildRound，KB 集合一致（`prefetchedUsable` 判定）即整体复用，检索只跑一遍；集合不一致丢弃预取、链路以免登录口径自检。
4. 流式路径（CsStreamService）同步接入预取复用，但**闸门不对称**：`CsVisitorService.send` 为 `hits.isEmpty() && !hasExecutableTools(...)`（A1B 放宽），`CsStreamService` 仍为 `hits.isEmpty()` 即兜底——流式下即使绑定了可执行工具也不会放行。**残留，待补**（对齐 send 口径后再宣称对称）。

取舍兑现：省一次全量 KB 检索管线；绕过检索缓存的风险被消除——预取结果本身就是 ChatRetrievalSupport 产物（searchOutcome 同一缓存键口径），无跨角色串号面。

**A3 门禁接线（半天工作量）**

`CsGovernanceFacadeImpl.canPublish` 委托 `ReleaseGateService.evaluate`（只读评估、不写执行记录），保留原有 status/model/prompt 快速失败。取舍得失：客服渠道应用模板从「能起服务」升级为「评测达标」，放弃的是无评测基线空间的灵活性——ReleaseGate 已有豁免（waived）机制兜底。

### 批次 B：编排层收口（智能密度）——**已全部交付（2026-11-18）**

实施记录（与原方案的差异点一并记录）：

- **B1 信号收口**：`CsTurnSignals`（意图/情绪/重复进线/轮次/负面连击）由 `CsTurnSignalService` 在 send() 入口一次计算，写入会话三列（last_intent_code / sentiment_streak / last_sentiment_score）。情绪分析**上移复用**：`SentimentAnalyzer` SPI + 词表实现从 callcenter insight 迁到 `callcenter-common.sentiment`（零依赖层，实现去 @Component 由两侧配置类注册 Bean，CS 侧 @ConditionalOnMissingBean 允许 LLM 实现接管）；连击阈值与语音洞察 C4 同口径（-0.35）。散落 classify 的旁路点迁移为后续演进（缓存/缺口/辅助的上下文各不相同，强行共享会破坏各自语义）。
- **B2 规则引擎**：`CsHandoffRuleEngine` 纯静态求值，规则四级 KEYWORD → SENTIMENT → REPEAT → TURN_LIMIT；渠道 `handoff_rules` JSON **整体替代**内置默认（未写出的类型视为不启用），坏 JSON 降级默认；内置默认=关键词+情绪阈值连 2 轮+24h 重复进线第 2 次开启、轮次上限默认关。**范围裁剪如实记录**：敏感词 BLOCK 与知识零命中仍是流程内固有闸门（依赖后续结果，无法在入口求值），不进引擎；keywordHandoff 改名语义为「规则触发转人工」，reason 记录命中规则便于归因。
- **B3 指标补维**：`CsMetricService.rebuild` 按 (stat_date, workspace_id, channel_code) 幂等拆行——全渠道行 + 每渠道行；新增 repeatContactRate（当日会话中同访客 24h 内已有过进线的占比）与 containmentRate（未建单即终结占比）；`CsMetricScheduler` 每日 04:00 定时重建（独立 boolean 开关默认关，cron 可配，逐空间容错）；看板加渠道列与两张指标卡。
- 意图维度精确重复判定留待后续：历史会话的 last_intent_code 随时间回填后才有数据（本轮起开始落）。



**B1 每轮信号统一：`CsTurnSignals`**

在 `send()` 入口算一次，全链路共享，替代散落 classify：

```java
record CsTurnSignals(String intentCode, String intentName, String sentimentLabel,
                     double sentimentScore, int repeatTotal24h, int turnCount, int sentimentStreak) {}
```

- 情绪：**上移复用**，不在客服域新写。`SentimentAnalyzer` SPI 与 `LexiconSentimentAnalyzer` 从 callcenter insight 包移到 `forge-callcenter-common`（零业务依赖层，依赖方向允许 customer-service 引用），客服文本侧走词表版，后续可挂 LLM 实现。注意：词表版是 callcenter 的通话洞察口径（中文客服词表），文本场景先小样本校准再上阈值。
- 意图：主链路 classify 一次，结果同时喂给 语义缓存白名单 / 坐席辅助 / 缺口归并（旁路点改为消费信号，不再各自算）。

**B2 转人工规则收口：`CsHandoffRuleEngine`**

把 5 处散落 if 收敛为有序规则链，每条规则产出 `HandoffDecision(hit, ruleType, reason)`。规则存储取舍：

- 方案甲：渠道新列 `handoff_rules`（JSON），改动最小，运营可调，先 JSON 后建表；
- 方案乙：新表 `agent_cs_handoff_rule`（priority + rule_type + params + enabled），与意图规则表同构，便于管理页。
- **建议甲先行**（与敏感词 / 关键词的渠道列先例一致），规则超过 10 条或需要独立 CRUD 时再升表。
- 首批内置规则：关键词（迁入）、敏感词 BLOCK（迁入）、零命中（迁入）、**情绪阈值（≤ -0.35 连续 2 轮）**、**重复进线（24h 内同访客第 2 次同意图进线）**、**轮次上限（bot 连答 N 轮未解决，可配）**。
- 模型辅助判定预留接口（与 A3 意图 LLM 分类同一个演进点），规则命中即转、模型只作加分——落实对标取舍①。

**B3 重复进线率指标**

`CsMetricDaily` 加 `repeatContactRate` / `containmentRate`（bot 会话中未建单即终结的占比）；重建逻辑按 `(workspace_id, visitor_id, 意图, 24h)` 窗口统计。同时 `channel_code` 拆维：rebuild 目前只写一行汇总（`channel_code` 恒 null），改为「每渠道一行 + 全渠道一行」，看板加分组视图。**接入定时重建**：SnailJob 已被排除，按项目纪律用独立 `@Scheduled` + enabled 开关（复用 SLA 调度器模式，默认 04:00，与留存清理 03:00 错峰）。

### 批次 C：工具护栏（风险控制，对标取舍②落地）——**C1/C2/C3/C5 已交付（2026-11-18），C4 残留**

实施记录：

- **C1 分级**：`agent_tool` 加 `risk_level`(READ/WRITE/HIGH_RISK,默认 READ)/`action_key`(幂等键模板,`{param}` 占位符按入参展开,任一占位缺失退化为工具级键——宁可多拦不漏拦)/`daily_limit` 三列。
- **C2 归属下推**：渠道 `identity_binding` 列；护栏上下文 `CsChatFacade.GuardContext` 随请求透传（ChatSendBo → AgentSession 瞬态字段，沿用 callerWorkspaceId 先例）→ `ToolAssembler.registerIfAbsent` 统一装饰（审批门之后最后一道，实体映射未命中的 MCP/内置工具原样透传）；**未配置 identity_binding 的渠道 WRITE/HIGH_RISK 一律 deny**（fail-closed），拦截与执行都写审计。
- **C3 幂等与额度**：新表 `agent_cs_action_log`（uk conversation_id+action_key）；占位语义重构为显式 `Reservation(logId, duplicate)`（第一版用「null 既表示重复又表示占位成功」是真缺陷，测试抓出后修正）；FAILED 允许重试；`daily_limit` 走 Redis 原子计数日窗口，**Redis 不可用（含静态初始化失败的 LinkageError）降级放行**——额度是增益不是正确性闸门。
- **C5 审计**：WRITE/HIGH_RISK 全量留痕 + READ 失败留痕（state 为 ERROR/DENIED/INTERRUPTED 或执行抛异常）；参数经 `CsPiiMasker` 脱敏；结果摘要取 ToolResultBlock output 的 TextBlock 文本（与 WorkingMemoryGuard 同口径）。
- **C4 明确残留**：ask 模式异步化（立即回执 + 审批中心回调后执行）需要「审批中心 → 工具执行」回调桥，审批单创建后无执行入口会造成假挂起——单独一期做，本批 ask 模式在客服链路保持原同步等待语义。
- 写入的 `agent_cs_action_log`/`agent_cs_audit_log` 为客服域表但由 forge-agent 护栏直接 JDBC 写入——与 `CsGovernanceFacadeImpl` 读 agent_info 同口径（护栏必须落在工具装饰层，跨模块契约反而拆散执行链）。

**C1 工具风险分级**

`agent_tool` 加三列：`risk_level`（READ / WRITE / HIGH_RISK，默认 READ）、`action_key`（幂等业务键模板，如 `refund:{orderNo}`）、`daily_limit`（动作级日限次）。SQL 走既有幂等 CALL 模式。

**C2 归属校验：下推业务系统，平台强制传递与审计（ADR-02）**

平台不接业务库、不知道订单表结构，自建归属校验等于把业务域拉进客服模块。方案：

- 工具参数强制注入 `visitorId` / `channelCode` / `conversationId` 上下文（平台侧注入，模型与前端均不可伪造）；
- HTTP 类操作工具的请求头由平台附加业务系统的访客凭证（渠道配置 `identity_binding`：外部 token / 手机号验证码 / 访客 claim 三种绑定方式可选）；
- 归属判定由业务系统在其接口内完成，平台只保证「凭证不可绕过 + 调用全留痕」。
- 取舍：放弃平台内集中校验的「一眼可见」，换取业务边界不失控；未配置 identity_binding 的渠道，WRITE/HIGH_RISK 工具直接 deny（fail-closed，与 D8 同口径）。

**C3 操作幂等与额度**

- 新表 `agent_cs_action_log`：`uk(conversation_id, action_key)`，工具调用前占位、重复命中直接返回上次结果摘要；
- 动作级额度：复用 Redis 原子计数基建（渠道限流同款），键 `forge:cs:action:{workspace}:{visitor}:{tool}` 日窗口，超限转人工 + `QUOTA_BLOCK` 审计（与 token 配额共用 `CsQuotaService` 的决策结构）。

**C4 操作类 HITL 改造**

现状 `ApprovalGateTool.ask` 同步等待人工（默认 120s 超时），客服访客在线等不起。客服场景改为：ask 命中 → 立即回执「已提交，等待确认」→ 写 `agent_cs_action_log` 状态 PENDING → 坐席在工单侧审批 → 结果经 `cs_ticket_event` 推给访客。取舍：访客多一次异步等待，换取审批不阻塞 SSE 连接；工单成为天然的审批载体，不新造审批入口。

**C5 调用审计**

`CsToolGuard`（包装 ApprovalGateTool 之后的最后一道）在每次工具调用后写 `agent_cs_audit_log`：eventType=TOOL_CALL，detail 含工具名 / 风险级 / 参数摘要（过 `CsPiiMasker`）；结果码与耗时进 detail 且落结构化列 `result_code` / `duration_ms`（`agent_cs_c5_audit_columns.sql` 幂等升级 + 01-schema 折列）。READ 成功不留痕（防日志量失控），失败全量留痕。

### 批次 D：发布与回流（治理闭环）

> **状态（2026-11-19）**：D2 已交付；D1 未启动。
> D2 落地三件事：① badcase「标记评测」直写 `agent_eval_case`（`source=cs_badcase`，取代导出 JSON 人工导入）；
> ② 坐席人工结案后按比例采样（默认 10%，`cs.eval.sample-rate`；要求访客 ≥2 轮、无 badcase 记录）；
> ③ 发布门禁校验「最近一次评测是否针对当前 `config_hash`」，过期直接阻断。
> 两条来源写入的都是**待确认态**（`review_status=0`），运营在坐席看板「回流用例」抽屉确认后才参与评测运行；
> 幂等靠 `uk_eval_case_source(source, source_ref_id)`。

**D1 灰度发布（ADR-03）**

- 数据已有：`agent_version.snapshot_json` 不可变快照 + `agent_info.published_version`。缺的是「按会话锁版本」：
  - `agent_info` 加 `rollout_percent`（默认 100，0=灰度关闭）；
  - 会话创建时按 `hash(visitorId) % 100 < rollout_percent` 决定走快照版还是现行版，结果写入 `agent_cs_conversation.pinned_version`，**同会话后续轮次全部用同一版本**（否则体验跳变——这是灰度正确性的关键，比分流算法本身重要）；
  - 对话链路支持「按快照装配 Agent 配置」（`AgentVersionService.buildSnapshot` 已有反向还原的基础，需补 contextAssembler 按 snapshot 覆盖 model/prompt/tools 的取数路径）——这是本批唯一的「重」改动。
- 范围控制：只对客服域生效，控制台聊天不引入（存量会话零行为变更，与 D1 客服分支收敛口径一致）。
- 取舍：快照版配置是「发布时刻冻结」，灰度期间修 prompt 不生效——这正是灰度的语义，但要在运营文档写清。

**D2 评测回流闭环**

- badcase「标记评测」从导出 JSON 改为直接写 `agent_eval_case`（表已在），带来源标记 `source=cs_badcase`；
- 人工处理完成的会话按比例（默认 10%，可配）采样生成评测用例：坐席 resolve 时若会话有 ≥2 轮访客消息且无 badcase 记录，落一条 `agent_eval_case`（question=访客原话，reference=坐席最终回复，pending 人工确认）；
- 回归链路：客服 Agent 发布前（批次 A3 接入门禁后）自动跑对应评测集，低于门禁分阻断发布——**这一步把「人机闭环」从文档语义变成代码事实**，是对标旁路设计的完整落地。

## 四、架构决策记录（ADR）

### ADR-01：知识命中从「闸门」降级为「信号」

- **状态**：Accepted（终态形态修订：A1B 过渡 + A1 终态信号已实施 2026-11-18；「删除预检」不再执行——A2 后预检即链路同构检索本身，且流式路径需要生成前闸门）
- **背景**：CS 层用知识命中预判兜底，导致工具类意图短路、检索双跑；根因是 ChatSendVo 缺兜底信号。
- **决策**：过渡期闸门加「无工具」条件（方案 B）；终态由 facade 返回信号判定，CS 层删除预检。
- **后果**：得——查询类意图可达 L3 工具层，检索成本减半；失——纯知识缺口场景多一次模型调用，需意图白名单快速短路弥补。

### ADR-02：归属校验下推业务系统，平台只做凭证传递与审计

- **状态**：Accepted（批次 C2 已交付，2026-11-18）
- **实施记录**：`CsChatFacade.GuardContext` 随请求透传（conversation/visitor/workspace/channel/identityBindingEnabled）→ ChatSendBo → AgentSession 瞬态 → buildRound → `ToolAssembler.registerIfAbsent` 统一装饰 → `CsToolGuardService`；渠道 `identity_binding` 列随 `agent_cs_c5_tool_guard.sql` 落库；未配凭证的 WRITE/HIGH_RISK deny 与幂等/日限次由 C3 承接。**残留**：C4 异步 HITL 回调桥未做（READ 失败审计已于 2026-11-19 补齐）。
- **背景**：访客无登录态，订单归属无法在平台侧校验；平台直连业务库会让客服模块吞噬业务域。
- **决策**：平台强制注入访客上下文 + 渠道配置 identity_binding，归属判定由业务系统接口内完成；未配置凭证的渠道 WRITE/HIGH_RISK 工具一律 deny。
- **后果**：得——业务边界不失控，接入方按自身数据模型校验；失——平台无法独立保证归属正确性，接入质量依赖文档与模板（电商模板内置 identity_binding 预设）。

### ADR-03：灰度按「会话锁版本」而非「按轮次分流」

- **状态**：Proposed（批次 D）
- **背景**：agent_version 快照已存在但对话链路不消费；灰度若按轮次分流，同会话中途换模型/提示词，体验跳变且归因污染。
- **决策**：分流只在会话创建时判定一次，版本写入 `agent_cs_conversation.pinned_version`；灰度仅客服域生效。
- **后果**：得——归因干净、体验连续、可按会话维度对比 canary/stable 指标；失——快照冻结，灰度期配置修改不生效；需补对话链路按快照装配的取数路径（本批主要工作量）。

## 五、明确不做（延续 docs/02 纪律）

1. 不引 WebFlux / Kafka / Nacos / 独立规则引擎（规则链先 JSON 列后建表，不上 Drools）；
2. 平台不自建订单归属库、不直连业务系统数据源；
3. 情绪识别不自研新引擎，复用上移后的 SentimentAnalyzer SPI；
4. 灰度不做多实验组正交分层（A/B/C 组互斥是运营问题，一个 rollout_percent 够用）；
5. 评测引擎不自建（复用 agent_eval_* 平台表，客服只做写入方）；
6. 操作审计不做全量 READ 留痕（日志量失控，只记 WRITE / HIGH_RISK / 失败）。

## 七、结论

对标文档是一张「理想态架构图」，ForgeAgent 在**接入层安全、工单与坐席旁路、横切追踪**三处已经超出它的设计；差距不在「画了没画」，而在四个执行断点：工具被知识闸门短路（L3 名存实亡）、护栏缺业务级校验（L4 只有平台口径）、编排信号散落无收口（L2 靠旁路拼凑）、发布无灰度且门禁半接线（旁路闭环缺最后一环）。批次 A 是半天到一天量级的正确性修正，应最先落地；批次 C 决定这套客服能否承接真实交易场景；批次 D 补上「数据回流 → 迭代」的最后一段，使人机闭环从设计意图变成代码事实。
